# Defensive decoy responses for hostile anonymous 404s

Adds a middleware that intercepts 404 responses and, for anonymous users hitting paths that could never have been valid, swaps the honest 404 for a decoy HTTP 200 so scanners get no signal that the path was missing. 90% of decoys are the exact plain-text body `these are not the droids you are looking for`; 10% are a gzip-encoded payload that decompresses to 50 MiB. The decision logic is split into pure helpers (`is_exempt_path`, `build_decoy_response`) with an injectable RNG, and the middleware is registered before `session_resolution` so session resolution runs outermost and populates `request.state.user` first. Logged-in users, standard web files (`/robots.txt`, `/favicon.ico`, `/sitemap.xml`, `/.well-known/*`), and "might-have-been-valid" paths (image extensions, `/images/`, `/`, `/events/...`, and a known top-level route list) are exempt and keep their real 404.

Watch for: the gzip bomb allocates a real 50 MiB buffer in server memory on every bomb response (confirmed) — a per-request server-side cost, not just a client-side hazard. The exemption list hardcodes `/admin` as a known top-level route, but there is no top-level `/admin` route in the app (confirmed) — so a common attacker probe is exempted from the decoy, weakening coverage. The forced-branch end-to-end tests re-implement the middleware body instead of calling `decoy_404_middleware`, so the production integration path is only exercised on the default (un-forced) RNG (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The exemption logic implements the requirement's three clauses (logged-in, standard web file, might-have-been-valid), and cross-checking against the real router tree confirms every genuine top-level route is covered. The one mismatch is `/admin`: it is in the exemption list but is not a real top-level route (admin lives under `/events/{event_path}/api/admin/...`), so probes to `/admin` get an honest 404 instead of a decoy — a coverage gap in the defense, not a correctness break.

The gzip bomb is safe on the wire (~50 KB compressed, no conflicting Content-Length because Starlette derives it) but materializes the full 50 MiB decompressed buffer in server memory for each bomb response. Under a burst of hostile scanning — exactly the traffic this feature attracts — that is a self-inflicted memory amplification worth bounding.

Test coverage is broad on `is_exempt_path` and on `build_decoy_response`, but the forced-branch end-to-end tests bypass the real middleware entrypoint and re-implement its logic inline, so a regression inside `decoy_404_middleware` itself would not necessarily be caught by the forced-branch cases.

### Exemption logic vs. the requirement's three clauses

The requirement carves out three categories that must keep an honest 404: logged-in users, standard web files, and "might-have-been-valid" paths. `is_exempt_path` plus the middleware's user check map onto these: the logged-in check reads `request.state.user` and returns the original 404 when a user is present; standard web files are the exact `/robots.txt`, `/favicon.ico`, `/sitemap.xml` set plus the `/.well-known/` prefix; and "might-have-been-valid" is covered by image extensions, `/images/`, `/`, `/events/`, and a top-level route allow-list.

Cross-checking the allow-list against the actual router tree: the genuine top-level routes are `/` (events list), `/login`, `/logout`, `/register`, `/lost-rockets`, the `/static` mount, and everything under `/events/{event_path:path}` (which is where admin, reports, scan, and review routes actually live). The `/events/` and `/static` exemptions plus the top-level list cover all of these. The prefix matching (`path == route or path.startswith(route + "/")`) avoids false matches like `/loginx`, which the tests assert.

The one divergence is `/admin` (confirmed): there is no top-level `/admin` route — admin endpoints are `/events/{event_path}/api/admin/...`. Exempting `/admin` means an anonymous probe to `/admin` receives an honest 404 rather than a decoy, which is precisely the kind of reconnaissance this feature aims to blind. This doesn't violate the requirement (it errs toward honesty, the safe direction), but it leaves a gap on a high-signal probe path.

### Gzip bomb construction and server-side cost

```python
compressed = gzip.compress(b"\0" * BOMB_DECOMPRESSED_SIZE)
return Response(content=compressed, status_code=200,
                media_type="text/plain", headers={"Content-Encoding": "gzip"})
```

On the wire this is bounded: 50 MiB of zeros compresses to ~50 KB (confirmed), and no explicit `Content-Length` is set, so Starlette derives it from the actual compressed bytes and the advertised length can't contradict the payload. The 50:1 decompression ratio is a modest bomb.

The concern is server-side: `b"\0" * BOMB_DECOMPRESSED_SIZE` allocates a fresh 50 MiB bytes object on every bomb response, and `gzip.compress` runs the DEFLATE pass over all 50 MiB each time. The compressed output is constant, so this is pure waste that scales with hostile traffic — the exact traffic profile this middleware invites. Precomputing the compressed bytes once at import and reusing them removes both the allocation and the recompression from the request path.

### Middleware ordering

`decoy_hostile_404` is defined before `session_resolution`, and because Starlette runs the last-added `@app.middleware("http")` outermost, `session_resolution` wraps the decoy and runs first on the request, populating `request.state.user` before the decoy inspects the response. The decoy reads `request.state.user` with `getattr(..., None)`, so a missing attribute degrades to "anonymous" rather than raising. `read_only_guard` returns 403 (not 404) for read-only events, so it never collides with the decoy path.

### Test coverage and meaningfulness

`is_exempt_path` is thoroughly tabled (true and false cases, including case-insensitivity and the `/loginx` non-match), and `build_decoy_response` is tested on both branches via forced RNGs plus a loose probabilistic ratio check.

The gap is in the end-to-end tests. `_build_app` has two paths: when `rng is None` it calls the real `decoy_404_middleware`, but when an `rng` is injected it re-implements the middleware body inline (`call_next`, status check, user check, `is_exempt_path`, `build_decoy_response(rng=rng)`). Every forced-branch e2e test (`test_anonymous_bogus_path_returns_plain_decoy`, `..._returns_gzip_bomb`, `test_logged_in_user_gets_real_404`, the exemption cases) passes an `rng`, so they exercise the test's copy of the logic, not `decoy_404_middleware`. A regression introduced inside the production middleware — inverting the user check, dropping the exempt check — would not be caught by these cases, because they never run that code. The production middleware also calls `build_decoy_response()` with no RNG, so the 10% bomb branch is never exercised through the real entrypoint at all. Making the production middleware accept an injectable RNG (and threading it through) would let the e2e tests force branches against the real code path and close both gaps.
